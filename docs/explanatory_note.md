# ВВЕДЕНИЕ

Курсовой проект посвящён разработке веб-сервиса для ведения дневника реабилитации после травм и инсультов с отслеживанием прогресса. Разработанное приложение получило название «Точка опоры». Оно связывает индивидуальные назначения специалиста, записи пациента и представление накопленной истории. Результатом является работающее клиент-серверное приложение, которое можно запустить локально и продемонстрировать без отдельной установки сервера базы данных.

При длительном восстановлении важно сохранять последовательную историю занятий. Устные сообщения не всегда позволяют восстановить дату, объём нагрузки и причины пропусков. Свободные заметки в мессенджере удобны для общения, но не имеют устойчивой структуры. Электронная таблица позволяет хранить числа, однако сама по себе не связывает их с назначениями и не разграничивает доступ пациента и специалиста. Разрабатываемый сервис решает именно задачу структурированного учёта.

Объектом разработки является процесс информационного сопровождения индивидуальной реабилитационной программы. Предмет разработки — программные средства хранения планов, регистрации занятий, контроля доступа и расчёта показателей выполнения. Система не ставит диагнозов, не подбирает упражнения автоматически и не интерпретирует записи как медицинское заключение. Значения целевой нагрузки вводятся специалистом; демонстрационные назначения иллюстрируют работу интерфейса.

Цель проекта — реализовать веб-сервис, обеспечивающий ведение индивидуального дневника и просмотр динамики выполнения реабилитационного плана. Для достижения цели необходимо определить роли и сценарии, построить модель данных, разработать REST API, реализовать браузерный интерфейс, сформулировать правила расчёта прогресса и проверить ограничения с помощью автоматических тестов.

В проекте применены Java, Spring Boot, Spring Data JPA и Spring Security. Для локального хранения используется H2. Браузерный интерфейс создан на HTML, CSS и JavaScript без внешних клиентских библиотек. Такой состав позволяет сосредоточиться на предметной логике и воспроизводимом запуске. Применение JPA соответствует модели доступа к реляционным данным, описанной в официальном руководстве Spring [2].

Работа содержит разделы функционального назначения, проектирования и конструирования программного продукта. В приложениях представлены руководство пользователя, сценарий демонстрации, описание API и контрольные примеры. Все сведения о выполненных проверках относятся к фактически собранной версии проекта; результаты испытаний на реальных пациентах не заявляются.

# 1.   Функциональное назначение программного средства

## 1.1 Классы решаемых задач

В рамках проекта реабилитационный план рассматривается как ограниченный по времени набор ежедневных назначений. У плана есть пациент, цель, дата начала, дата окончания и состояние. Назначение определяет упражнение и целевой объём в конкретной единице. Запись дневника отражает то, что пациент сообщил о занятии в определённую дату: выполненный объём, субъективную боль, самочувствие и комментарий.

Разделение плана и факта необходимо для корректного анализа. Отсутствие записи не доказывает, что упражнение не выполнялось; оно означает только отсутствие сведений. Явный пропуск, напротив, является сообщённым пациентом результатом. Выполненное занятие с объёмом ниже цели также отличается от пропуска. Поэтому система хранит статус занятия отдельно от численного результата и не подменяет один показатель другим.

Один пациент может иметь несколько планов в истории, но одновременно активен только один. Такое ограничение упрощает объяснение текущих назначений и предотвращает неоднозначный подсчёт регулярности. При изменении программы специалист завершает старый план и создаёт следующий. Исторические назначения остаются связаны с записями, поэтому новые целевые значения не изменяют смысл уже накопленной информации.

Для упражнения используется одна из трёх единиц: повторения, минуты или метры. Эти единицы нельзя суммировать в общий физический результат. Сервис строит отдельные ряды по каждому назначению. Общие показатели используются только там, где имеется одинаковый смысл счётчика: количество ожидаемых занятий, число выполненных, число пропущенных и число занятий без записи.

Обмен информацией организуется между пациентом и закреплённым специалистом. Ответ специалиста хранится при записи дневника и относится к её текущей редакции. Если пациент меняет факт нагрузки или комментарий, прежний ответ очищается. Это предотвращает ситуацию, когда старое замечание выглядит как реакция на новые данные. Сам факт редактирования сохраняется в журнале операций.

В проекте сопоставляются классы решений, а не проводится маркетинговое исследование конкретных коммерческих продуктов. Бумажный дневник прост и доступен без технических средств, но не позволяет автоматически строить выборки и проверять дубли. Электронная таблица упрощает численные расчёты, однако требует ручного поддержания структуры. Мессенджер обеспечивает обмен сообщениями, но поиск занятий по датам и упражнениям остаётся неформальным.

Специализированный сервис объединяет план, факт и права доступа. Он требует разработки правил и проверки ошибок, зато обеспечивает единый формат записи. В отличие от системы мониторинга жизненных показателей, дневник не ограничивается приёмом измерений и созданием тревог. В отличие от системы технического обслуживания, его центральным объектом является самоотчёт пациента о занятии, а не акт выполнения работы сотрудником.

За основу организации кода принят многослойный подход, встречающийся в предоставленных учебных проектах. При этом предметные сущности, правила дневника, расчёт показателей, интерфейс и тесты реализованы для собственной темы. Текст пояснительной записки согласован с действительным поведением приложения, а не переносит описание функций других проектов.

## 1.2 Функциональное назначение

Система предусматривает роли PATIENT, SPECIALIST и ADMIN. Пациент работает только со своей карточкой, планами и дневником. Он не может добавлять назначения и менять состояние программы. Специалист просматривает закреплённых пациентов, создаёт их планы, наполняет справочник упражнений и отвечает на записи. Доступ к чужому пациенту отклоняется даже при прямой подстановке идентификатора в URL.

Администратор имеет доступ ко всем карточкам и журналу операций. Он может создать пациента с выбранным специалистом и выполнить действия сотрудника над планом. Однако даже администратор не может создавать записи дневника от имени пациента. Это ограничение сохраняет происхождение фактических сведений: дневник заполняет тот пользователь, которому он принадлежит.

В прототипе нет самостоятельной регистрации. Учётная запись пациента создаётся одновременно с карточкой. Специалист может закрепить нового пациента только за собой, администратор — за выбранным специалистом. Начальные служебные пользователи создаются при первом запуске. Управление персоналом, восстановление пароля и его смена через интерфейс оставлены за границами текущей реализации.

Пользовательские требования описывают доступные действия, а системные — ограничения, которые проверяются независимо от интерфейса. Спецификация представлена в таблице 2.

Основным требованием воспроизводимости является запуск одной собранной Java-программы с браузерным интерфейсом. Версия Java для компиляции установлена равной 17. Spring Boot 3.5 требует Java не ниже 17; допустимые версии среды определяются документацией платформы [1]. Фактическая сборка комплекта выполнена на JDK 23.0.2 и Maven 3.9.9. Наличие байткода Java 17 не подменяет отдельные испытания на каждом JDK.

Данные должны сохраняться между перезапусками. По умолчанию применяется файловая H2. Рабочая база исключается из архива исходников; в комплект не включены записи пользователя. Для тестов используются отдельные базы в памяти. Драйвер PostgreSQL присутствует как возможность конфигурации, однако совместимость реального развёртывания на PostgreSQL в данной работе отдельно не проверялась.

Ошибки должны быть понятны пользователю и иметь соответствующий HTTP-статус. Формы проверяют обязательность и численные границы, но решающая проверка выполняется на сервере. Интерфейс должен корректно отображать русские символы, не зависеть от внешних шрифтов и адаптироваться к узкому экрану. Поддержка клавиатуры обеспечивается обычными элементами form, button, label и dialog.

Прототип рассчитан на небольшой учебный набор данных. Для истории плана используются списки без постраничной загрузки; журнал администратора ограничен страницами по 30 записей. Измерения пропускной способности и времени отклика под нагрузкой не проводились. Поэтому требования к числу одновременных пользователей и эксплуатационной доступности не заявляются как достигнутые.

Сервис работает локально на 127.0.0.1. Публикация в интернете потребовала бы отдельного развёртывания с HTTPS, управлением учётными записями, миграциями схемы, резервным копированием и эксплуатационными процедурами. Эти задачи не смешиваются с проверенными возможностями локальной учебной версии.

# 2    Проектная часть

## 2.1 Архитектура приложения

Выбрана архитектура монолитного веб-приложения. Браузер получает статические ресурсы от того же сервера, к которому обращается за JSON. Сервер включает встроенный Tomcat, Spring MVC, слой бизнес-логики, репозитории и ORM. Общий источник интерфейса и API упрощает сессионную аутентификацию и не требует отдельной настройки межсайтового доступа.

HTTP-слой представлен ApiController. Он принимает DTO, запускает проверку Bean Validation и вызывает сервис. Контроллер не рассчитывает прогресс и не решает, к какому пациенту имеет доступ пользователь. Эти правила сосредоточены в RehabService, чтобы проверка не зависела от того, какая кнопка отображалась в браузере.

Сервисный слой управляет транзакциями. Операция создания записи включает проверку владельца, состояния плана, даты, уникальности и сохранение аудита. При ошибке транзакция откатывается. Репозитории предоставляют операции чтения и сохранения сущностей. ProgressCalculator выделен отдельно как чистая вычислительная часть без зависимости от HTTP и базы.

Браузерный клиент хранит текущее состояние выбранного пациента и плана. После изменения он перечитывает данные с сервера, а не предполагает, что локальная копия остаётся актуальной. Динамические строки экранируются перед выводом. Графики представлены SVG, построенным по численным рядам, полученным из API.

Рисунок 2 — Архитектура приложения «Точка опоры»

На уровне кода используются Service Layer, Repository, DTO и Dependency Injection. RehabService задаёт транзакционные операции предметной области. Интерфейсы JpaRepository инкапсулируют доступ к данным, Requests и Views отделяют формат HTTP от сущностей, а зависимости передаются в конструкторы средствами Spring.

Spring MVC выполняет роль Front Controller через DispatcherServlet. Сервер возвращает JSON, представление строится браузером. Состояния плана реализованы перечислением и проверками переходов; отдельных классов паттерна GoF State нет. Хранение состояния аутентификации в сессии означает, что API не является полностью stateless.

Пароли хранятся как BCrypt-хеши. Учётная запись загружается по логину через UserDetailsService. Доступ к бизнес-функциям проверяется в сервисе по реальной роли Account, а не по данным из тела запроса. Затем проверяется связь пользователя с конкретным пациентом. Поэтому наличие роли специалиста само по себе не даёт доступ ко всем карточкам.

Сессия хранится в cookie с HttpOnly и SameSite=strict. Для изменяющих запросов используется CSRF-токен. После входа клиент запрашивает его повторно. Это соответствует принципу интеграции серверной CSRF-защиты с браузерным клиентом, изложенному в документации Spring Security [3]. Защита не отключается ради удобства тестирования; тесты явно передают токен.

Для сериализации применяются DTO, исключающие хеши паролей и лишние связи. Пользовательский текст экранируется при выводе в HTML. При экспорте CSV потенциальные префиксы формул в текстовых ячейках нейтрализуются апострофом, а кавычки удваиваются. Журнал содержит тип операции и идентификатор объекта, но не текст дневника.

Для активации плана применяется пессимистическая блокировка строки пациента. Два запроса одного пациента не могут одновременно пройти проверку отсутствия активного плана. После ожидания данные перечитываются. Версии RehabPlan и DiaryEntry дополнительно обнаруживают устаревшие действия пользователя. Уникальные ограничения БД обеспечивают ещё один уровень защиты от дублей.

Такой набор мер является частью учебной реализации и не обозначает прохождения независимого аудита безопасности. Не выполнялись сертификация, клинические испытания и оценка соответствия законодательным требованиям медицинской эксплуатации. В проектной документации эти ограничения отделены от проверенных программных свойств.

## 2.2 Проектирование пользовательского интерфейса

Интерфейс разделён на экран входа и рабочую область. В рабочей области слева находится навигация, сверху — дата и выбор пациента для сотрудника. Пациенту список чужих карточек не показывается. Такое различие упрощает взаимодействие, но не считается механизмом защиты: все права повторно проверяются сервером.

На странице «Обзор» расположены цель плана, период, показатели и занятия на сегодня. Страница «Планы реабилитации» содержит историю программ и назначения выбранного плана. «Дневник занятий» представляет фактическую историю в таблице. «Мой прогресс» показывает отдельные графики. Сотрудник дополнительно получает справочник упражнений и карточки пациентов.

## 2.3 Модель данных ПС

Модель включает семь основных сущностей. Account хранит идентификатор входа, хеш пароля, имя и роль. Patient связывает учётную запись пациента с учётной записью специалиста и дополнительными данными карточки. Отдельная сущность пациента позволяет не помещать предметные медицинские сведения в универсальную таблицу аутентификации.

Exercise представляет элемент справочника. RehabPlan относится к пациенту и хранит период, цель, состояние и версию. Assignment связывает план со справочным упражнением и содержит снимок названия, инструкции, единицы и целевого объёма. DiaryEntry относится к конкретному назначению и дате. Связи между сущностями задаются внешними ключами JPA. Учётная запись имеет уникальный username. Связь Patient с пациентской учётной записью уникальна. Для Assignment действует уникальность пары plan_id и exercise_id. Для DiaryEntry — уникальность assignment_id и performed_on. Эти ограничения дополняют сервисные проверки и защищают целостность при конкурентных действиях.

В частности, поле passwordHash никогда не входит в UserView. Настройка open-in-view=false помогает удерживать границу работы с данными в сервисе.

Постоянная база находится в rehab-diary/data/rehab.mv.db. scripts/start.ps1 устанавливает рабочую папку перед запуском, поэтому путь ./data относится к корню проекта. Подключение задано в application.yml. Сущности отображаются Hibernate на таблицы, а репозитории выполняют операции чтения и сохранения.

## 2.4 Моделирование работы приложения

Новый план создаётся в состоянии DRAFT. В этом состоянии разрешено добавление и удаление назначений. Черновик не учитывается как действующая программа и не позволяет вести дневник. Его можно архивировать без активации; в этом случае количество ожидаемых занятий равно нулю.

Переход DRAFT → ACTIVE выполняет специалист. Система проверяет наличие хотя бы одного упражнения, неистёкший период и отсутствие другого активного плана. Будущая дата начала допустима: план уже зафиксирован, однако записи до начала периода запрещены. Это позволяет подготовить программу заранее без появления ложной просрочки.

Переход ACTIVE → COMPLETED прекращает изменение дневника. Если завершение произошло раньше планового конца, расчёт ожидаемых занятий ограничивается датой завершения. Если период уже истёк, конечной датой расчёта остаётся дата окончания. Система не завершает планы автоматически: решение подтверждает специалист.

Завершённый план может перейти в ARCHIVED. Архивирование не удаляет назначения и записи. Обратные переходы отсутствуют, что делает историю однозначной. Для нового набора упражнений создаётся отдельный план. В такой модели нет скрытого изменения условий, по которым оценивались прошлые занятия.

Рисунок 6 — Диаграмма последовательности активации плана

Пациент открывает форму и выбирает назначение текущего плана. Дата по умолчанию соответствует сегодняшнему дню, но допускается заполнение прошедших дней внутри периода. Перед сохранением сервер получает назначение и связанного пациента. Затем он проверяет, что автор записи совпадает с учётной записью пациента.

После проверки доступа транзакция блокирует строку пациента и перечитывает состояние плана. Блокировка нужна не только при активации: она согласует запись занятия с одновременным завершением программы. Если специалист завершил план первым, запись после ожидания получает конфликт. Если первой сохранилась запись, последующее завершение сохраняет её как часть истории.

Для DONE фактическая нагрузка должна быть положительной. Для SKIPPED она равна нулю, а комментарий обязан содержать причину. Численные значения дополнительно ограничены сверху; боль и самочувствие проверяются в собственных шкалах. После валидации система проверяет отсутствие записи того же назначения на ту же дату.

При сохранении создаётся событие аудита в той же транзакции. Ответ содержит актуальный DTO записи и её версию. Клиент перечитывает историю и прогресс. При исправлении запись сохраняет исходные назначение и дату; версия позволяет обнаружить, что другой участник уже изменил её после открытия формы.

Рисунок 7 — Диаграмма последовательности записи занятия

Прогресс представлен несколькими показателями, каждый из которых имеет самостоятельный смысл. Общее количество запланированных занятий S определяется как число назначений M, умноженное на число прошедших календарных дней D. День начала и текущий день включаются. Верхняя граница периода — наиболее ранняя из сегодняшней даты, даты окончания и даты досрочного завершения.

Для черновика или плана, который ещё не начался, D равно нулю. Для завершённого плана знаменатель больше не увеличивается. Если в плане два ежедневных упражнения и прошло три дня, S равно шести. Наличие будущих дат в периоде не увеличивает этот показатель заранее.

Количество выполненных занятий обозначается Ndone, явных пропусков — Nskip. Число занятий без записи равно S − Ndone − Nskip. Регулярность рассчитывается как 100 × Ndone / S. Если S равно нулю, интерфейс показывает 0 и отсутствие накопленных занятий; деление на ноль не выполняется.

Достижение целевого объёма рассчитывается отдельно. Занятие входит в Ntarget, если имеет статус DONE и фактическая нагрузка не ниже назначенной. Доля достижения равна 100 × Ntarget / S. Выполнение меньшего объёма повышает регулярность, но не увеличивает число достигнутых целей. Превышение цели не создаёт значения выше 100 процентов.

Например, за три дня при двух упражнениях пациент сообщил о четырёх выполнениях, одном пропуске и оставил одно занятие без записи. Регулярность составляет 4 / 6 × 100 = 66,7 процента. Если целевой объём достигнут в двух выполнениях, доля достижения равна 33,3 процента. Эти показатели описывают выполнение программы и полноту дневника, а не медицинскую эффективность.

Для графика берутся только выполненные занятия, упорядоченные по дате. По каждому назначению строятся фактическая нагрузка и линия целевого значения. Боль и самочувствие показываются в отдельных рядах этого же упражнения. Пропуск не превращается в нулевое значение графика, чтобы не смешивать отсутствие занятия с измерением способности.

# 3    Конструирование программного продукта

Сборка организована Maven. Файл pom.xml фиксирует родительскую версию Spring Boot 3.5.16, целевую Java 17 и зависимости. В набор входят web, data-jpa, validation, security, H2, PostgreSQL, springdoc и тестовые средства. Команда verify компилирует код, выполняет тесты и формирует исполняемый JAR.

Исходники размещены в пакете ru.coursework.rehab. Подпакет domain содержит сущности, repository — интерфейсы доступа к БД, service — бизнес-операции и расчёт, api — DTO, контроллер и обработчик ошибок, config — безопасность и начальные данные. Статические ресурсы находятся в src/main/resources/static. Тесты отделены в src/test/java.

RehabApplication запускает Spring Boot и задаёт Clock с конфигурируемой зоной. Централизованный источник времени позволяет использовать одинаковую календарную дату в дневнике и расчётах. Прямое чтение даты браузера не определяет серверные ограничения: пользователь не может разрешить будущую запись изменением часов своего устройства.

Первичная загрузка DemoData выполняется только для пустого набора учётных записей. Повторный запуск не сбрасывает данные. При включённом демонстрационном режиме создаются два вымышленных пациента, один активный план и записи за прошедшие дни. Все примеры предназначены для демонстрации форм и графиков, а не для воспроизведения реальной программы лечения.

ApiController выполняет транспортную роль. Requests объединяет входные record-типы, Views — выходные. ApiExceptionHandler переводит исключения в ответы с понятными статусами. Сервис достаточно компактен для учебной работы, но при расширении его целесообразно разделить на управление пациентами, планы и дневник. Текущая концентрация проверок упрощает обзор правил, однако не означает, что один крупный сервис оптимален для любой системы. Это осознанное ограничение масштаба прототипа.

## 3.2 Тестирование ПС

Проверка разделена на три уровня. Модульные тесты ProgressCalculatorTest проверяют расчёт без Spring и БД. Интеграционные ApiIntegrationTest запускают контекст приложения, реальные контроллеры, сервисы, JPA и цепочку безопасности через MockMvc. ConcurrencyTest выполняет две операции в независимых потоках и транзакциях.

В интеграционных тестах используются существующие учебные учётные записи и отдельная база H2 в памяти. Большинство действий выполняется с подставленным пользователем Spring Security Test, а отдельные проверки действительно отправляют логин и пароль. Поэтому проверка ролей не выдаётся за полное испытание всех механизмов управления учётными записями.

Тестовые методы с изменениями откатываются после выполнения. Конкурентный тест, напротив, создаёт свои данные в подтверждённой транзакции и запускает две реальные сервисные операции. CountDownLatch синхронизирует начало действий. Проверяется один успех, один конфликт и ровно один активный план в БД.

Дополнительно выполняется браузерный сценарий: вход пациента, запись занятия, просмотр графиков, переход к узкому экрану, выход, вход специалиста, ответ на запись, создание черновика и назначения. Снимки интерфейса сделаны в работающем приложении. Ошибки JavaScript и выход ширины документа за мобильный экран проверяются отдельно.

## 3.3 Создание документации

Готовый JAR включён в папку app. Скрипт start.cmd вызывает PowerShell, который ищет подходящий JDK и запускает сервер из корня проекта. Это фиксирует расположение файловой БД относительно проекта. Пользователю не нужно устанавливать Maven для демонстрации готового приложения.

Для самостоятельной сборки используется build.cmd либо Maven из IDE. Скрипт проверяет результат команды и обновляет готовый JAR только после успешного verify. Исходники и отчёты включены отдельно, поэтому комплект пригоден как для запуска, так и для изучения реализации.

Настройки переопределяются переменными окружения: порт, адрес БД, пользователь БД, пароль, календарная зона и начальные пароли. По умолчанию сервер доступен только локально. Обычный файл .env автоматически не читается. Изменение начального пароля в конфигурации не обновляет уже существующий хеш.

Резервная копия файловой базы создаётся при остановленном приложении. Не следует копировать открытый файл БД произвольным способом или запускать два экземпляра с одним путём. Для передачи чистого проекта рабочая база исключается, а демонстрационные записи формируются заново при первом запуске.

Текущая схема создаётся Hibernate с ddl-auto=update. Это удобно для учебной демонстрации, но не является контролируемой системой миграций. Развитие проекта предполагает добавление миграций, управления пользователями, проверки PostgreSQL и пагинации больших историй. Эти функции обозначены как направления развития, а не как уже реализованные.

Документация хранится рядом с исходниками: README.md описывает запуск; docs/API.md — маршруты и CSRF; docs/USER_GUIDE.md — действия пользователей; docs/TESTING.md и test-results — фактические проверки; docs/CODE_STRUCTURE.md — подробный разбор реализации. В docs/pz размещены изображения и редактируемые SVG-диаграммы.

Схема работающего API сохраняется в docs/openapi.json и доступна через /v3/api-docs. Swagger показывает методы, схемы входных объектов и ответы. Вход выполняется через основную страницу; для изменения данных нужен актуальный CSRF-токен.

package ru.coursework.rehab.service;
import java.time.*;
import java.time.temporal.ChronoUnit;
import java.util.*;
import ru.coursework.rehab.domain.*;
/** Показатели регулярности и фактической нагрузки. Не оценивают степень выздоровления. */
public final class ProgressCalculator {
    private ProgressCalculator() {}
    public record Point(LocalDate date,double amount,double target,int pain,int wellbeing) {}
    public record Series(Long assignmentId,String title,Exercise.Unit unit,double targetAmount,List<Point> points) {}
    public record Result(long scheduled,long done,long skipped,long unrecorded,long targetReached,
        double adherence,double targetAchievement,List<Series> series) {}
    public static Result calculate(RehabPlan plan,List<Assignment> items,List<DiaryEntry> entries,LocalDate today) {
        LocalDate until=today.isBefore(plan.endsOn)?today:plan.endsOn;
        if(plan.closedOn!=null && plan.closedOn.isBefore(until)) until=plan.closedOn;
        long days=plan.status==RehabPlan.Status.DRAFT || until.isBefore(plan.startsOn)?0:ChronoUnit.DAYS.between(plan.startsOn,until)+1;
        long scheduled=days*items.size();
        LocalDate limit=until;
        List<DiaryEntry> eligible=entries.stream().filter(e->!e.performedOn.isBefore(plan.startsOn)&&!e.performedOn.isAfter(limit)).toList();
        long done=eligible.stream().filter(e->e.status==DiaryEntry.Status.DONE).count();
        long skipped=eligible.stream().filter(e->e.status==DiaryEntry.Status.SKIPPED).count();
        long reached=eligible.stream().filter(e->e.status==DiaryEntry.Status.DONE&&e.actualAmount>=e.assignment.targetAmount).count();
        List<Series> series=items.stream().map(a->new Series(a.id,a.title,a.unit,a.targetAmount,
            eligible.stream().filter(e->e.assignment.id.equals(a.id)&&e.status==DiaryEntry.Status.DONE)
                .sorted(Comparator.comparing(e->e.performedOn))
                .map(e->new Point(e.performedOn,e.actualAmount,a.targetAmount,e.pain,e.wellbeing)).toList())).toList();
        return new Result(scheduled,done,skipped,Math.max(0,scheduled-done-skipped),reached,
            scheduled==0?0:100.0*done/scheduled,scheduled==0?0:100.0*reached/scheduled,series);
    }
}
