# Подготовка к защите

## Краткое выступление

Разработан веб-сервис «Точка опоры» для ведения дневника реабилитации после травм и инсультов. Основная задача — связать индивидуальные назначения специалиста с фактическими записями пациента и показать динамику выполнения плана.

Пациент видит свои данные и заполняет дневник. Специалист создаёт планы для закреплённых пациентов и оставляет ответы. Администратор просматривает все доступные карточки и журнал изменений.

Сервер реализован на Java и Spring Boot. Данные хранятся через JPA, интерфейс работает в браузере. Для простого локального запуска используется файловая база H2. Архитектура разделяет HTTP API, бизнес-логику и доступ к данным.

Особенность проекта — проверка бизнес-ограничений. У пациента может быть только один активный план; назначения после активации фиксируются. Для одного упражнения в один день допускается одна запись. Устаревшая версия не перезаписывает новые данные. Права на конкретного пациента проверяются на сервере.

Прогресс представлен регулярностью занятий, достижением целевой нагрузки и графиками отдельных показателей. Эти величины не называются процентом выздоровления. Минуты и повторения не складываются в одну оценку.

Выполнены модульные и интеграционные тесты, а также сценарий двух параллельных активаций планов. Дополнительно проверен интерфейс в браузере. Клиническая интерпретация показателей и интеграция с медицинскими системами в задачи учебного прототипа не входят.

## Показ на 5–7 минут

1. Пациент patient: обзор, цели, занятия, графики.
2. Добавить сегодняшнюю запись для упражнения, ещё не записанного сегодня.
3. Повторить создание — показать защиту от дубля.
4. Выйти, войти как doctor: увидеть запись и оставить ответ.
5. Выбрать patient2, создать черновик, добавить упражнение и активировать.
6. Показать, что назначения активного плана зафиксированы.
7. Войти как patient2: новый план доступен; данные первого пациента не видны.
8. При наличии времени показать CSV и журнал администратора.

Перед защитой сделайте копию папки data при остановленном сервере. Проверяйте сценарий заранее: записи сохраняются между запусками.

## Вопросы

**Чем отличается от ежедневника?** Запись связана с назначением, единицей нагрузки, периодом и целью; есть роли, ответ специалиста и расчёт регулярности.

**Как считается регулярность?** Выполненные занятия делятся на число ежедневных назначений за прошедшие дни, включая сегодня. Явный пропуск и отсутствие записи различаются.

**Почему выполнено, если цель не достигнута?** Занятие выполнено в некотором объёме. Достижение целевой нагрузки считается отдельно.

**Почему нельзя менять активный план?** Чтобы сохранять смысл старых записей и целевых значений. Изменения программы оформляются следующим планом.

**Что при двух одновременных активациях?** Транзакции блокируют строку пациента. Второй запрос после ожидания проверяет наличие активного плана и получает 409.

**Зачем версия записи?** Чтобы не перезаписать данные, изменившиеся после открытия формы.

**Почему H2?** Для показа без отдельного сервера БД. Драйвер PostgreSQL включён, но отдельная проверка на нём не проводилась.

**Почему нет машинного обучения?** Тема требует дневник и трекинг. В проекте используются проверяемые расчёты, без неподтверждённого прогноза выздоровления.

**Ограничения?** Ежедневное расписание, одно занятие упражнения в день, нет уведомлений, самостоятельной регистрации, экрана управления специалистами и смены пароля, нет клинической валидации.

**Что развивать?** Дни недели, несколько сессий в день, управление аккаунтами, миграции схемы и проверка PostgreSQL.
